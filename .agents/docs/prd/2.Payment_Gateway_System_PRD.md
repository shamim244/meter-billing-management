# Payment Gateway System — PRD
**Product:** NBPDCL SaaS Billing Platform
**Module:** Payment Gateway System
**Version:** 1.0
**Status:** Draft for Development

---

## 1. Purpose

This system handles all money coming into the platform — regardless of source. It must support three payment modes and feed every successful payment into the Wallet System and Billing & Subscription System.

**Three payment modes:**
1. Online Payment Gateway (Razorpay/similar)
2. Manual UPI
3. Bank Transfer (NEFT/IMPS)

---

## 2. Goals

- Allow tenants to pay via automated PG **or** manual methods, based on their comfort level.
- Keep a single, unified transaction ledger regardless of payment mode.
- Give admin full manual control over verifying non-automated payments.
- Support both **wallet top-up** and **direct subscription payment** flows.
- Support recurring auto-debit (UPI AutoPay) where possible for renewals.

---

## 3. Payment Modes — Detailed Spec

### 3.1 Online Payment Gateway (Automated)

| Item | Decision |
|---|---|
| PG Provider | Not finalized — Razorpay recommended (see §8) |
| Methods supported | UPI, Card, NetBanking, Wallets — all enabled |
| Primary method | UPI (~98% of expected volume) |
| Recurring/Auto-debit | Yes — UPI AutoPay mandate, if supported by chosen PG |
| Verification | Automatic via PG webhook + signature check |
| Settlement | Per PG provider's own settlement cycle (T+1/T+2 typical) |

**Flow:**
```
Tenant clicks "Pay via PG"
→ Backend creates PG order
→ Tenant redirected/shown PG checkout
→ Tenant completes payment (UPI/Card/NetBanking)
→ PG sends webhook → backend verifies signature
→ Payment marked SUCCESS
→ Wallet credited OR Subscription activated directly
→ Confirmation shown + notification sent
```

**Recurring (AutoPay) flow:**
```
Tenant sets up UPI AutoPay mandate during first subscription
→ On renewal date, PG auto-triggers debit
→ Webhook confirms → renewal processed automatically
→ If auto-debit fails → fallback to manual payment prompt
```

### 3.2 Manual UPI

| Item | Decision |
|---|---|
| Receiving UPI ID | Single UPI ID for all tenants (business account) |
| Proof required | UTR number — **mandatory** |
| Screenshot | Optional, supporting evidence only |
| Verification | Admin manually approves |
| Approval SLA | Same day, up to 24 hours (no strict guarantee) |

**Flow:**
```
Tenant selects "Pay via Manual UPI"
→ System displays business UPI ID + QR code
→ Tenant pays using their own UPI app
→ Tenant returns to platform, submits:
     - UTR number (mandatory)
     - Screenshot (optional)
→ Payment record created with status = PENDING_VERIFICATION
→ Admin sees it in Admin Panel → Pending Payments queue
→ Admin manually verifies against bank/UPI statement
→ Admin marks APPROVED or REJECTED
→ If APPROVED → Wallet credited / Subscription activated
→ If REJECTED → Tenant notified with reason, can resubmit
```

### 3.3 Bank Transfer (NEFT / IMPS)

| Item | Decision |
|---|---|
| Transfer types allowed | NEFT, IMPS (RTGS excluded) |
| Bank account | Single bank account for all tenants |
| Reference | Tenant enters their own transaction reference number |
| Verification | Admin manually, against bank statement |
| Approval SLA | Same as manual UPI — same day to 24 hours |

**Flow:**
```
Tenant selects "Pay via Bank Transfer"
→ System displays bank account details (A/C no., IFSC, name)
→ Tenant transfers via NEFT or IMPS
→ Tenant submits:
     - Transaction reference/UTR
     - Amount paid
     - Screenshot (optional)
→ Payment record created with status = PENDING_VERIFICATION
→ Admin verifies against bank statement
→ Admin APPROVES or REJECTS
→ If APPROVED → Wallet credited / Subscription activated
```

## 4. Two Payment Purposes (Applies to All 3 Modes)

Every payment — regardless of mode — is made for one of two purposes:

### A. Wallet Top-up
```
Amount paid → credited fully to tenant wallet
→ wallet_transactions (credit)
→ Used later for subscription + extra usage deduction
```

### B. Direct Subscription Payment
```
Amount paid → applied directly to subscription
→ Subscription activated/renewed immediately
→ Wallet NOT touched for this amount
→ But minimum wallet balance still required
   to cover potential extra usage (see Wallet System PRD)
```

Both purposes apply identically whether payment came via PG, Manual UPI, or Bank Transfer. The **mode** decides *how* money enters. The **purpose** decides *where* it goes.

---

## 5. Admin Controls

| Control | Description |
|---|---|
| Enable/disable payment method | Admin can turn off Manual UPI, Bank Transfer, or PG independently per tenant tier or globally |
| Minimum payment amount | Admin sets minimum top-up/payment amount (e.g. ₹500) |
| Pending payments queue | Admin dashboard lists all PENDING_VERIFICATION entries |
| Approve / Reject | Single-click actions with mandatory rejection reason field |
| Manual refund | Admin can manually refund any payment; no automated refund policy for now |
| Audit log | Every approve/reject/refund action logged with admin ID + timestamp |

## 6. Database Schema

```sql
-- Master payment record — one row per payment attempt, any mode
payments
├── id
├── tenant_id
├── mode                  -- 'pg' | 'manual_upi' | 'bank_transfer'
├── purpose               -- 'wallet_topup' | 'direct_subscription'
├── amount
├── currency              -- INR
├── status                -- 'pending' | 'pending_verification' | 'success' | 'failed' | 'rejected'
├── gateway_order_id       -- nullable, PG only
├── gateway_payment_id     -- nullable, PG only
├── utr_number             -- nullable, manual UPI / bank transfer
├── screenshot_url         -- nullable
├── bank_reference         -- nullable, bank transfer only
├── verified_by            -- admin_id, nullable
├── verified_at            -- nullable
├── rejection_reason       -- nullable
├── created_at
└── updated_at

-- Recurring mandate info (for PG auto-debit)
payment_mandates
├── id
├── tenant_id
├── gateway_mandate_id
├── status                 -- 'active' | 'paused' | 'cancelled' | 'failed'
├── created_at
└── updated_at

-- Admin action audit trail
payment_audit_log
├── id
├── payment_id
├── admin_id
├── action                 -- 'approved' | 'rejected' | 'refunded'
├── notes
└── created_at
```

## 7. Payment Status Lifecycle

```
PG Path:
initiated → pending → success/failed   (automatic, via webhook)

Manual UPI / Bank Transfer Path:
initiated → pending_verification → success/rejected   (manual, via admin)
```

## 8. Open Decision — PG Provider

Not yet finalized. Recommended shortlist:

| Provider | Notes |
|---|---|
| Razorpay | Most common for Indian SMB SaaS; strong UPI AutoPay + subscription API support |
| Cashfree | Competitive pricing, good UPI AutoPay support |

## 9. Notifications Triggered by This System

| Event | Notify |
|---|---|
| PG payment success | Tenant — confirmation |
| PG payment failed | Tenant — retry prompt |
| Manual payment submitted | Admin — new item in queue |
| Manual payment approved | Tenant — confirmation |
| Manual payment rejected | Tenant — reason + resubmit option |
| Auto-debit mandate failed | Tenant — manual payment fallback prompt |
