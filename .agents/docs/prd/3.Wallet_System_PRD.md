# Wallet System — PRD
**Product:** NBPDCL SaaS Billing Platform
**Module:** Wallet System
**Version:** 1.0
**Status:** Draft for Development
**Depends on:** Payment Gateway System (must be built first)

> **Terminology note:** This platform uses **Agent / User (`user_id`)** — the term "Tenant" is not used anywhere in this document or the codebase.

---

## 1. Purpose

The Wallet System holds a prepaid INR balance per Agent (user). It is the single source of truth for:
- Subscription renewal payments
- Extra/billable usage deductions
- All money movement that isn't a Direct Pay (see Payment Gateway PRD §4)

Every other system (Billing & Subscription, Usage Tracking) reads and writes balance only through this system — never directly.

---

## 2. Goals

- One wallet per Agent — fully isolated, never shared.
- Credit wallet automatically when Payment Gateway confirms a successful payment.
- Debit wallet automatically for subscription renewal and billable usage events.
- Maintain a complete, immutable transaction ledger — every rupee movement traceable.
- Never allow balance to go negative through normal Agent activity.
- Allow Admin to manually adjust balance (credit or debit, including into negative) with mandatory reason logging.
- Trigger low-balance and critical-balance alerts before the Agent gets blocked or renewal fails.

---

## 3. Confirmed Business Rules (Your Answers)

| Question | Decision |
|---|---|
| Can balance go negative? | **No**, not through normal Agent usage. **Admin can force it** (manual override) with logged reason. |
| Does wallet balance expire? | **No expiry.** Balance stays until used or refunded. |
| Can Agent withdraw/refund wallet to bank? | **Not decided yet** — treated as open item, default = non-refundable via self-service; Admin manual refund only (per Payment Gateway PRD §5). |
| Daily transaction limit? | **No platform-enforced default.** Agent can optionally set their **own** limit if they want one. Admin can also set a limit if needed later. Not mandatory for v1. |
| Shared wallet across multiple Agents under one parent? | **No.** Every Agent has a **separate, independent wallet.** No parent/shared wallet concept exists. |

## 4. Wallet Balance Rules

```
Balance starts at ₹0 when Agent account is created.
Balance only increases via:
   - Successful payment (any of the 3 modes) with purpose = wallet_topup
   - Admin manual credit adjustment

Balance only decreases via:
   - Subscription renewal deduction
   - Billable usage event deduction (from Usage Tracking System)
   - Admin manual debit adjustment

Normal deduction NEVER allowed to push balance below ₹0.
If deduction would cause negative balance:
   → Deduction is BLOCKED
   → Corresponding action (renewal / usage event) fails gracefully
   → Agent notified: "Insufficient wallet balance"

Admin override is the ONLY path to a negative balance,
and every such action is logged with a mandatory reason.
```

---

## 5. Wallet Thresholds & Alerts

*(Carried over from earlier finalized rules — confirm final ₹ values at Plan Management stage, since these can be plan-specific)*

| Threshold | Action |
|---|---|
| Balance < ₹500 (default, admin-configurable) | Low balance alert sent to Agent |
| Balance < 1 month's base subscription price | Critical alert — "renewal at risk" |
| Balance = ₹0 | Block new billable usage events |
| Balance cannot cover next renewal | Subscription → `RENEWAL_DUE` → `GRACE_PERIOD` (per subscription lifecycle) |

**Pre-renewal check (must run before renewal date, not on it):**
```
If (balance − upcoming_renewal_amount) < minimum_alert_threshold
→ Notify Agent BEFORE renewal date, not after
```

## 6. Database Schema

```sql
-- One wallet per Agent — strictly 1:1, never shared
wallets
├── id
├── user_id            -- FK to users (Agent), UNIQUE — enforces 1 wallet per Agent
├── balance             -- current balance, decimal(12,2)
├── currency             -- INR (fixed for now, upgrade path to credits later)
├── low_balance_threshold      -- nullable, Agent's own optional limit
├── daily_txn_limit            -- nullable, Agent's own optional limit
├── is_frozen                  -- boolean, Admin can freeze a wallet
├── created_at
└── updated_at

-- Immutable ledger — every single balance movement, no exceptions
wallet_transactions
├── id
├── wallet_id            -- FK to wallets
├── user_id              -- FK to users (denormalized for fast queries)
├── type                  -- 'credit' | 'debit'
├── amount
├── balance_after          -- snapshot of balance after this transaction (audit safety)
├── source                 -- 'payment_topup' | 'subscription_renewal' |
                            --   'billable_usage_event' | 'admin_adjustment' | 'refund'
├── reference_type          -- 'payment' | 'subscription' | 'usage_event' | 'admin' 
├── reference_id            -- FK to relevant record (payments.id, etc.)
├── admin_id                -- nullable, set only for admin_adjustment
├── reason                  -- nullable, MANDATORY when source = admin_adjustment
├── created_at
└── (no updated_at — ledger rows are never edited, only inserted)

-- Admin manual adjustment log (subset view of wallet_transactions, for audit UI)
wallet_admin_adjustments
├── id
├── wallet_transaction_id   -- FK
├── admin_id
├── type                     -- 'credit' | 'debit'
├── amount
├── reason                   -- mandatory, free text
└── created_at
```

**Critical rule:** `wallet_transactions` is **insert-only**. Never update or delete a row. If a correction is needed, insert a reversing transaction — this preserves a fully honest audit trail, which matters a lot given this handles real money for real Agents.

## 7. Integration Points

### 7.1 From Payment Gateway System
```
Event: PaymentSuccessEvent (purpose = wallet_topup)
→ Wallet System listens
→ Credits wallet.balance += payment.amount
→ Inserts wallet_transactions (type=credit, source=payment_topup)
```

### 7.2 To Billing & Subscription System (built later)
```
Subscription System calls:
   WalletService::debit(user_id, amount, source: 'subscription_renewal', reference_id: subscription_id)

Wallet System responds:
   - SUCCESS → balance updated, transaction logged
   - INSUFFICIENT_BALANCE → subscription system handles fallback
     (grace period, block renewal, notify Agent)
```

### 7.3 To Usage Tracking System (built later)
```
Usage Tracking System calls:
   WalletService::debit(user_id, amount, source: 'billable_usage_event', reference_id: event_id)

Same success/failure contract as above.
If INSUFFICIENT_BALANCE → billable action itself should be blocked
BEFORE it's recorded as delivered (don't give the service, then fail to charge).
```

### 7.4 Admin Panel
```
Admin can:
- View any Agent's wallet balance + full transaction history
- Manually credit or debit (mandatory reason field)
- Freeze/unfreeze a wallet (blocks all debits, e.g. for disputed accounts)
- Export wallet ledger per Agent (for support/dispute resolution)
```

**Admin Wallet Adjustment — Must Be Easy, One-Click Simple**

This is a core requirement, not a secondary admin tool. Admin must be able to increase or decrease any Agent's wallet balance quickly, without friction:

```
Admin opens Agent's wallet page
→ Sees current balance clearly
→ Two simple actions available:

   [ + Add Balance ]   → enter amount + reason → instant credit
   [ − Deduct Balance ] → enter amount + reason → instant debit

→ No approval chain, no multi-step process
→ Reason field is mandatory (for audit trail — see §6, wallet_transactions.reason)
→ Balance updates immediately, visible on same screen
→ Logged automatically in wallet_transactions + wallet_admin_adjustments
```

**Why this must be simple:**
Admin will use this frequently — correcting errors, handling support disputes, manual goodwill credits, fixing failed auto-deductions, and (in future) issuing referral/coupon credits manually before those systems are automated. A clunky multi-screen flow here creates daily friction for whoever runs support.

**UI requirement:** This action should be reachable in **2 clicks maximum** from the Agent's profile/wallet view — not buried in a settings menu.

## 8. Wallet Service — Core Methods (for dev reference)

```
WalletService::credit(user_id, amount, source, reference_type, reference_id)
WalletService::debit(user_id, amount, source, reference_type, reference_id)
    → returns SUCCESS or INSUFFICIENT_BALANCE, never throws for business-logic failure
WalletService::adminAdjust(user_id, admin_id, type, amount, reason)
    → the ONLY method that can push balance negative
WalletService::getBalance(user_id)
WalletService::getTransactionHistory(user_id, filters)
WalletService::freeze(user_id, admin_id, reason)
WalletService::unfreeze(user_id, admin_id, reason)
```

**Rule for all debit calls:** wrap in a DB transaction with row-level locking on the wallet row, to prevent race conditions if two billable events try to deduct simultaneously (e.g. two API calls processing bills for the same Agent at once). This matters more than it looks — concurrent debits are the most common source of wallet bugs.

## 11. Future Roadmap (Not Built Now — Noted for Architecture Awareness Only)

These are **not part of this build**. They are noted here only so the Wallet System's schema doesn't accidentally block them later.

### 11.1 Refer & Earn (Future)
```
Concept: Agent refers another Agent → both get wallet credit on
         successful signup/first payment.

Why it's noted here now:
wallet_transactions.source already supports adding a new value later
   e.g. 'referral_bonus'
No schema change needed today — just confirming the ledger design
already accommodates a new source type without breaking anything.
```

### 11.2 Coupon / Promo Codes (Future)
```
Concept: Admin creates a coupon code → Agent applies it →
         wallet gets credited, or subscription gets a discount.

Why it's noted here now:
Same reasoning — wallet_transactions.source can later add
   e.g. 'coupon_redemption'
This system's ledger design (insert-only, source-tagged) is
already future-proof for this without rework.
```

**Action for now:** Nothing to build. Just don't hardcode `source` as a fixed enum with only today's values baked rigidly into the database layer if it can be avoided — keep it as a simple string/lookup so new source types can be added later without a migration that touches existing rows.
